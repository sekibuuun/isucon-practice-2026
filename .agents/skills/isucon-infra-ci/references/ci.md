# 対象環境の実行制御と結果の照合

## 事前確認

サービス・DB・負荷生成の配置、割当CPU・メモリ・ディスク、環境識別子、接続先、認証、操作主体を調べる。接続、コード反映、初期化、再起動、ベンチ、成果物回収について、リポジトリやユーザーが示した既存コマンド・管理ツール・CIの契約を確認する。存在しないコマンドやAPIを仮定しない。

対象環境で性能を比較する前に、環境識別子、対象SHA、配置と資源、初期データ、負荷条件、warm/cold、診断設定をrunへ記録する。負荷生成がサービスと資源を共有する場合は競合を記録し、条件を揃えた練習上の比較として扱う。公式スコアとは区別する。

分析のみの依頼でpush・反映・再起動・ベンチを行わない。許可済みの操作範囲内なら毎回の確認は不要だが、環境構築、コスト増、削除、対象追加は別の権限が必要。操作経路が未提供なら勝手に構築せず、その部分は未実施と報告する。

## 起動・待機・結果

操作前に対象環境、対象SHA、コマンドまたは操作入力、起動前時刻をrunへ記録する。SSHや環境管理コマンドで直接操作する場合も、対象を再確認し、実行コマンドと終了状態を記録する。CIや非同期ジョブを使う場合は処理ID・URL等を照合し、最新の一件を無条件に選ばない。

GitHub Actionsが既存の操作経路である場合の調査・照合例。WORKFLOW、BRANCH、SHA、RUN_IDは確認済みの値へ置換する。

```sh
gh workflow view WORKFLOW
gh run list --workflow WORKFLOW --branch BRANCH --commit SHA --json databaseId,headSha,status,conclusion,createdAt,url
gh run view RUN_ID --json headSha,status,conclusion,url,jobs
gh run view RUN_ID --log-failed
```

workflowを使う場合は名前・入力・trigger・ref、認証、結果保存先、変更対象SHAをcheckoutする契約を確認する。workflow_dispatchはdefault branch上にworkflowが必要。dispatch応答からrun IDが得られるとは仮定せず、workflow・SHA・時刻・実験識別子で新規runを照合する。候補が曖昧なら状態を確認し、再dispatchしない。

workflowのheadShaと、入力で指定してcheckoutするアプリSHAが異なる構成もある。両者を別々に記録し、runの検索にはworkflowのSHA、計測対象の確認には実際に反映されたアプリSHAを使う。headShaだけをアプリの反映証明にしない。

処理識別情報を記録したら、その処理を完了まで追う。短い状態確認・利用可能な待機手段を使い、待機中も進捗を伝える。通信断や中断から復帰した場合は同じ処理を確認する。失敗・cancelled・timeoutでも途中反映され得るため対象状態を調べる。

反映処理の成功とベンチの有効結果は別。公式起動が非同期なら公式ジョブIDで完了・採点結果まで確認する。対象SHA、ベンチvalidity、エラー、スコア、条件、ログ・プロファイル原本を記録する。取得する成果物に秘密情報を含めない。

## 排他・復旧

同一対象環境の構築・反映・再起動・ベンチは共通の環境単位で排他する。コマンド、ターミナル、workflow、ブランチ等の単位だけでは、別の操作経路からの干渉を防げない。

連続処理は一つの排他区間で反映→検証→ベンチを行うか、連携した環境ロックを維持する。分離した操作の間に別反映が入らない契約を確認する。稼働中の構築・反映・ベンチを新しい処理で自動cancelしない。待機順を保証とみなさず、完了SHAを毎回確認する。

候補の性能退行も修正前後の結果を人間へ提示して判断を待つ。却下されたら候補だけをコードでrevertし、同じ操作経路で反映・復旧検証する。must修正は保持する。schema復旧でデータを消す操作は自動選択しない。再起動追試では初期化がデータを消す前に、ベンチ中の書き込みが取得できることを確認する。

## 実行場所

練習では、ローカル環境、物理サーバー、仮想環境、コンテナ、クラウド等の種類ではなく、確認済みの対象環境と操作契約に従う。可能なら負荷生成をサービスから分離する。同居する場合は資源競合を含む条件を記録して揃える。本番では許可された競技サーバーと公式ベンチマーカーだけを使う。対象外の実行環境へ競技サービス処理を移さない。診断の静的解析や取得済み成果物の解析は別環境でもよい。
