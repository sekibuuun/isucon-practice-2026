# キャッシュ判断


TTLは「十分短ければ正しい」とは限らない。即時整合性が必要な競技仕様ならTTLだけでは満たせない。古い値・デフォルト値を返す方式は仕様上許容される場合だけ使う。

keyには結果を変えるユーザー、権限、query、版等を含める。権限別のHTMLを全ユーザーへ共用しない。更新・削除・権限変更・initializeに伴う削除または世代変更を設計する。遅い旧世代生成が新世代へ書き戻す競合も確認する。

同一keyの生成をsingleflight等でまとめる場合、生成中の更新、context終了、エラーの共有、再確認を考える。全体ロック下の重いI/Oや巨大な無制限mapを避ける。KVSアクセスにもN+1があるので、必要ならバッチ取得する。

キャッシュ喪失時に正本から復元できること、複数台の更新が伝播することを確認する。起動前の手動warmupだけに依存せず、CIの再起動・初期化・cold状態でも仕様とスコアを確認する。永続化が必要な生成結果と、再生成可能なキャッシュを区別する。
