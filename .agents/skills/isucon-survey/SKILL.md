# 全体調査とボトルネック一覧

[競技ルール](../isucon-workflow/references/regulations.md) と [共通ループ](../isucon-workflow/references/loop.md) を読む。同一作業中の再読込は不要。surveyは複数の対象を列挙する調査段階であり、一件の性能改善はユーザーの選択後にworkflowが担当する。

1. 依頼範囲、仕様、サービス・DB・負荷生成の配置と資源、初期化・ベンチ方法、既存の操作経路・計測手段を確認する。操作は [実行制御](../isucon-infra-ci/references/ci.md)、計測は [isucon-measure](../isucon-measure/SKILL.md) の必要な手順を使う。measureの一対象への絞り込みは選択後に行い、ここでは複数候補を列挙する。専門資料のrunへの記録指示は、surveyではsurvey.mdへ記録する。
2. [一覧・記録の管理](references/catalog.md) に従い調査IDと保存先を確定する。初回はテンプレートを使い、再調査は既存のID・履歴を読み込む。
3. 有効な基準ベンチ1回を基本に、同時間帯のHTTP・SQL集計・OS／主要プロセス指標を取得する。HTTPはメソッド・URI群別の回数・総時間・平均・分位点・転送量、SQLは総時間・回数・平均・走査行数、OSはCPU・I/O待ち・メモリ・ディスク・ネットワークを見る。既存手段があればGoプロファイルも取得する。取得失敗や負荷不成立は記録し、必要な再計測を行う。
4. 集計上位を横断して関連コードを必要な範囲だけ確認する。同じ原因を指す観測は調査記録で関連付け、一覧ではAPIごとに行を分ける。単一指標から制限要因を断定せず、原因は確認済み・推定を区別する。全SQLの実行計画、全ハンドラーの精読、個別再現実験、計測基盤の新規構築は行わない。
5. [一覧・記録の管理](references/catalog.md) に従い、API別に同一時間窓のHTTPログを集計し、合計応答時間の降順に並べる。原因・根拠・関連コードは調査記録へ残す。原因・改善余地・実装負担による総合順位付けは行わない。
6. 「順位・API・回数・合計応答時間・平均応答時間」の一覧と調査記録を保存・提示して終了する。候補が得られなければ空の一覧と不足計測を報告する。自動でworkflowを起動したり、対象を選択・実装したりしない。

時間・試行予算を守り、取れなかった指標と判断できない事項を明示する。短時間という理由で必要なログ保存・検証を省かず、権限や計測経路が不足する場合は不足を報告する。詳細な原因検証と改善は、ユーザーの選択後に [isucon-workflow](../isucon-workflow/SKILL.md) が担当する。
