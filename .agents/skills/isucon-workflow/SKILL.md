# ISUCONの一ボトルネック改善

最初に [競技ルール](references/regulations.md) と [ループ・記録・レビュー](references/loop.md) を読む。既存の依頼と許可範囲を確認し、ブランチ別記録から現在状態を復元する。

1. ユーザー指定の候補IDとsurveyの一覧・調査記録を読み、specに参照を残す。対象未指定なら一覧を提示して選択を待ち、一覧がなければ [isucon-survey](../isucon-survey/SKILL.md) を案内する。全体から対象を自動選定しない。仕様、対象環境、保守・初期化手順、操作経路、スコア計算、当日ルールを調べる。サービス・DB・負荷生成の配置、資源、環境識別子、接続・反映・再起動・ベンチ・成果物回収方法を推測しない。
2. 試行ごとに環境・対象SHA・条件・試行IDとログ原本の保存先・取得方法を確認して基準値を測り、試行後に原本を保存する。surveyの基準値はSHA・差分・環境・条件が一致し原本が確認できる場合のみ再利用し、不一致なら測り直す。計測・保存できなければ不足を報告する。
3. 選択された対象の原因が現在も成立するかログで検証し、同じ対象の改善候補を比較して今回実装する一候補を `spec.md` に書く。原因を区別できるログがなければ候補を選ばず追加計測する。必要なスキルだけを読む。
4. 選んだ候補だけを実装・検証し、mustを修正してセルフレビューする。確認済みの経路で計測用に反映・ベンチし、原本と結果を `run.md`・`review.md` に記録する。一覧更新のため全体の軽いHTTP・SQL・OS集計も比較ベンチで取得する。
5. 修正前後の有効スコア、SHA、条件、ばらつき、エラー、根拠ログを人間へ提示し、採用・却下・再計測の判断を待つ。判断前に正式採用・恒久反映しない。
6. 採用なら正式反映し、[一覧更新手順](../isucon-survey/references/catalog.md) に従って結果を一覧・調査記録・履歴へ反映して終了する。却下なら候補だけを取り消して復旧を確認し、一覧にも復旧後の根拠を反映し、同じボトルネックの候補選定へ戻る。再計測なら同じ候補を測り直す。別のボトルネックへ進まない。

| 観測・作業 | 読むスキル |
|---|---|
| 根拠不足、アクセスログ・OS・プロファイル | [isucon-measure](../isucon-measure/SKILL.md) |
| Go CPU、割り当て、ロック、HTTP、テンプレート | [isucon-go](../isucon-go/SKILL.md) |
| SQL総時間、N+1、実行計画、接続待ち | [isucon-db](../isucon-db/SKILL.md) |
| キャッシュ対象・整合性・重複計算 | [isucon-cache](../isucon-cache/SKILL.md) |
| nginx、OS、構成管理、反映・再起動 | [isucon-infra-ci](../isucon-infra-ci/SKILL.md) |

同じCodexがスキルを読み分ける。共通資料は同一作業中に再読込せず、専門資料は必要な箇所だけ読む。必要なコマンド・試行は省かない。改善に使うどのスキルでも、判断に使うログ原本の保存先・時間窓・試行IDをrunに残す。大量ログは集計と原本参照で扱う。

競技終了前は正式な操作経路で再起動・データ保持・起動順依存・ベンチ再現を確認する。最良の検証済み状態、未解消must、未検証事項を報告する。

ツールの詳細を確認する場合は [参考サイト](references/sources.md) を参照する。
